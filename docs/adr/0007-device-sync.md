# 端末どうしの同期 — 比べる・聞く・端末ごとの値を戻すのはコア

## Status

accepted（2026-10-09。handball-project#506）。2026-10-10 にシェルが「上書き」を外した（handball-project#518 — 下の「実装追記」）

## 文脈

記録アプリの利用者が、1 台で記録した試合を家族の端末でも見ていて、記録を足したり直したりすると
端末の間でずれる。これまでの受け渡しは 1 試合ずつの試合ファイル（SAMPLE_DTO_V2）で、受け取るたびに
ID を振り直して**別の試合**として取り込むので、送り直すと同じ試合が 2 つ並ぶ。

シェル側は、近くにある 2 台の端末をアプリどうしで直接つなぎ、全記録を交換して 1 回の操作で両方を
同じ中身にする、と決めた（サーバーも iCloud の自動同期も使わない）。形は 2 つ:

- **上書き** — どちらかの端末の中身で、もう片方を丸ごと置き換える（2026-10-10 に外した）
- **そろえる** — 試合・fact・チーム・選手を ID ごとに比べ、新しい方を採る

どちらも「何を採るか」の判断で、ドメイン規則の検証も絡む。判断はコアに置く（ADR 0005）。

## 決定

### 1. 計画は純粋関数、保存は発火層（ADR 0005 と同じ 2 層）

`src/sync/` に純粋関数を置く。時刻は `now` で受け取り、ID は作らない。

| 関数 | 役割 |
|---|---|
| `reconcile(local, remote, answers, now)` | そろえる。問いがあれば `Questions`、なければ `Merged` |
| `materialize(incoming, local)` | 届いた中身を、保存する端末の端末ごとの値で戻す |
| `encode_sync_payload` / `decode_sync_payload` | 端末の間を運ぶ形 |

保存は `ffi_write::apply_sync(repo, incoming)`。店の最新の記録を読み直して `materialize` し、
`SyncWriteRepository::replace_all` で店全体を 1 トランザクションで入れ替える。

**比べるのは始めた側の端末だけ**。できた中身を相手へ送り、両方の端末がそれぞれ `apply_sync` する。
両方が同じ比較を別々にしないので、結果が食い違わない。

### 2. 記録ごとに後勝ち。比べる中身から端末ごとの値を除く

記録（試合・fact・チーム・選手）は `SyncStamp { updated_at, deleted_at }` を持つ。削除は論理削除で、
消した記録も運ぶ（片方にしか無いものが「足した」のか「相手で消した」のかを見分けるため）。

- 片方にだけある → 足す / 中身が同じ → そのまま / 中身が違う → `updated_at` の新しい方（聞かない）
- 比べる単位は記録ごと（項目ごとではない）。試合と fact は別の記録なので、片方でタイトルを直し、
  もう片方で fact を足しても両方残る
- **試合の削除は「試合として最後に変わった時刻」（試合とその fact の `updated_at` の最大）と比べる**。
  試合の `updated_at` は fact の変更で進めない（進めると、別の端末で直したタイトルが、fact を
  足しただけの側に負けて戻る）

比べない値（`sync/compare.rs`）:

| 記録 | 値 | 理由 |
|---|---|---|
| 試合 | `is_home_on_left` | スコアの左右配置。見方の設定として端末ごとに持つ |
| 試合 | 端末内動画の `external_id` | 端末ごとに違う参照。同じ動画かは `cloud_identifier` で見る（どちらかが無ければ同じとみなす） |
| 選手 | `photo` | 写真は端末ごとに持ち、運ばない |

`materialize` は、保存する端末に同じ記録があればこれらをその端末の値に戻す。端末内動画が違う動画に
なった試合と、その端末に無かった端末内動画の試合は `VideoRelink` で返し、シェルが引き直す。

### 3. 規則で決められないものだけを聞く

| 問い | 場面 | 答え |
|---|---|---|
| `SameTime` | 両方にあり、`updated_at` がまったく同じで中身が違う | 選んだ側の版 |
| `DeletedThenChanged` | 片方で消した後に、もう片方で変わっていた | 消すか、変えた版を残すか |
| `MergedMatchInvalid` | 両方の直しを合わせた試合が規則（試合・fact・fact の列）に合わない | 選んだ側の試合を丸ごと |
| `CopiesDiffer` | 端末をまたぐ同じ試合の写し（ID が違う）の中身が違う（決定 7） | 選んだ側の写しを残す |

- **聞いて選ばれた版は `now` で書き直す**。次にどの端末と比べても選ばれた版が新しいので、同じ結果になる
- `MergedMatchInvalid` は、問いのない状態でそろえた結果を検証して出す。**片方の版そのままの試合は
  検証しない**（その端末で保存するときに検証を通っている）。答えた後にもう一度呼ぶと、問いが段階的に
  返ることがある。シェルは問いが返らなくなるまで繰り返す
- **片方で消した試合には `MergedMatchInvalid` を出さない**。消した試合が生きているのは
  `DeletedThenChanged` で残すと答えたときだけで、生きている側の版を選んだのと同じなので、聞かずに
  その側を丸ごと採る（聞いて消した側を選ばれると、残すと答えた試合が消える）
- 同じ記録を両方で直したときは聞かない。前回の同期からどちらが直したかを知るには相手ごとの前回の
  状態が要り、持たずに聞くと、片方だけが直した普通の場合まで毎回聞くことになる。代償として古い方の
  直しは黙って失われる

### 4. 参照されている記録は消さない

消されていない試合・fact・選手が参照するチームと選手は、消されていても戻す（`now` で書き直す）。
片方で使われていなかったチームを消し、もう片方でそのチームの試合を足していた、のような組み合わせで
起きる。参照先の無い記録を残さないことを、消したことより優先する。

### 5. 時刻はミリ秒に丸めて比べる

シェルの時刻は、端末の型（Swift の `Date` は秒を倍精度で持つ）から FFI の `SystemTime`（ns）へ変わり、
**往復すると 100 ns 程度ずれる**。そのまま比べると、同期済みの同じ記録が次の同期で「`updated_at` が
同じで中身（`recorded_at`）が違う」に見える。比べる前に全時刻を最も近いミリ秒に丸める（`sync/normalize.rs`）。
切り捨てにしないのは、ずれが負の向きに出ると 1 ms 手前へ落ちるため。

### 6. 運ぶ形は試合ファイルと別。版を先に見る

`SyncPayload { format_version, device_id, snapshot }` を JSON にする。中身はコアの型の serde 表現で、
**試合ファイル（SAMPLE_DTO_V2）とは別の形**。同期は両方の端末が同じ版の形を持つときにしか起きないので、
旧版のアプリが読める必要は無い。`decode_sync_payload` は `format_version` を先に読み、違えば中身を
読まずに `UnsupportedFormatVersion` を返す。

- f64 は JSON を往復しても 1 bit も変えない（`serde_json` の `float_roundtrip`）。変わると、同期済みの
  同じ fact が「中身が違う」に見える
- `device_id` は相手の表示と、自分自身とつながっていないかの確認にだけ使う。記録ごとには持たない
- **形を変えたら `SYNC_FORMAT_VERSION` を上げる**。コアの型の serde 表現もこの形の一部

### 7. ID の違う写しは、まだ同期していない端末をまたぐ組だけを 1 つにする（突き合わせ）

試合ファイル（SAMPLE_DTO_V2）で受け取った写しは、試合・fact・チーム・選手とも元の端末と別の ID を
持つ。そのまま比べると全部が「片方にしか無い」になり、同じ試合が 2 つ並ぶ。記録ごとの比較より先に
`sync/pairing.rs` を通す。

- **同じ試合の見分け方**: fact の「記録した時刻と種類」（印）が、**印の少ない側の半分以上**で一致するか。
  取り込みは `recorded_at` を残し、試合ファイルは秒までしか書かない（切り捨て）ので、写しの時刻は
  秒ちょうどになる。印が一致するのは、種類と秒が同じで、**ミリ秒まで同じか、片方が秒ちょうど**のとき。
  fact の無い試合は日付（秒）と両チームの名前
  - 端末で記録した時刻はミリ秒まで持つ。同じ試合を 2 台で別々に記録すると、前半開始やゴールを同じ秒に
    押していてもミリ秒が食い違うので、写しとみなさない（別々の記録を写しとみなすと、`CopiesDiffer` の
    答えで片方の記録が丸ごと消える。問いの文言も「同じ試合の写し」なので利用者が気づけない）
  - 半分以上を求めるのは、別の人の記録の試合ファイル（秒ちょうど）が手元の記録と偶然同じ秒に当たる
    ことがあるため。写しなら、どちらかで fact を足したり消したりしていても少ない側の印のほとんどが一致する
- **1 つにするのは、まだ同期していない端末をまたぐ写しの組だけ**
  - 中身が同じ → 聞かずに小さい方の ID に。中身は ID を使わずに比べる（チームは名前、選手は名前と
    背番号、fact は記録した秒と中身。時刻はミリ秒まで）
  - 中身が違う → `CopiesDiffer` で聞き、答えた側の ID と中身を残す（写しの `updated_at` は取り込んだ
    時刻なので、新しさの比較に使えない）。残した写しは `now` で書き直す
- **まとめない組**（別の試合として残し、`SyncDuplicateGroup` で知らせる）:
  - 同じ端末の中の写しどうし — どちらが新しい版かを、写しの `updated_at`（取り込んだ時刻）からは
    決められない。利用者が見て消す
  - どちらかの ID が両方の端末にある組 — 同期した後に、従来の試合ファイルで写しが届いた場合。
    同期済みの試合がその試合を表していて、写しは別の試合として足す
- **チームと選手**: 組にした写しのホーム同士・アウェイ同士で、**名前が同じ**チームを 1 つにする
  （残す側へ）。選手は背番号と名前が同じ人をまとめ、残りはまとめた先のチームへ移す。まとめるチーム・
  選手を参照していた記録（ほかの試合を含む）は付け替えて `now` で書き直す。名前の違うチーム
  （取り込みで別名の既存チームに紐付けたもの）はまとめない
  - **行き先はチームの組ごとに 1 つ**。写しの組ごとの「消す側のチーム → 残す側のチーム」を向きの無い
    つながりとして組にし、残す側として最も多く選ばれたチーム（同じなら ID の小さいチーム）へ組の全部を
    まとめる。2 台が互いに試合ファイルを送り合っていると、写しの組ごとに残す側が逆になり、向きのまま
    まとめると互いに相手へ付け替え合って、参照のある両方が決定 4 で戻る（同じ名前のチームが 2 つ残る）
- 消す側の写し（試合・その fact・まとめたチームと選手）は `now` で消す。まだ古い写しを持つ端末と
  後で比べても、消した方が新しい
- まとめた選手の写真は運ばない（決定 2）。写しの側にしか写真の無かった選手は、写真なしになる

## 実装追記

- **シェルが「上書き」を外した（handball-project#518）**。同期の形はそろえるだけになった。上書きは
  合わせる側のスナップショットをそのまま `materialize` に渡すだけで、コアに上書き専用の関数は無かったので、
  関数と FFI の形は変えていない（コメントと、この ADR の文脈だけ直した）。上書きは「合わせられる側を
  削除の記録ごと空にしてから、そろえる」と同じ結果になる — 空の側とそろえると、相手の記録と削除の記録が
  そのまま入る。`materialize` の「ここに無い記録は消す」もそのまま（そろえた中身は、採らなかった記録も
  削除の記録として持つ）
- **突き合わせ・そろえるの不具合 3 件を直した（handball-project#510）**。どれも 0.12.0 の実装で、利用者の
  答えやまとめた結果で、チームが二重になるか記録が消える経路だった。FFI の形は変えていない（挙動だけ）
  - チームが 2 つ残る — 票の向きのまま行き先にしていた。チームの組ごとに行き先を 1 つにした（決定 7）
  - 別々の記録を写しとみなす — 印を 1 つ共有すれば写しとしていた。ミリ秒の一致と半分以上を求めた（決定 7）
  - 残すと答えた試合が消える — 片方で消した試合にも `MergedMatchInvalid` を聞き、消した側を選ぶと
    `replace_whole_match` が削除済みの版を書き直していた。聞かずに生きている側を採るようにした（決定 3）
  - 再現テストは `tests/sync_tests.rs` の `copies_exchanged_both_ways_leave_one_team_and_player_per_name`・
    `separate_recordings_of_the_same_match_are_not_copies`・`match_file_sharing_less_than_half_of_the_prints_is_not_a_copy`・
    `match_kept_after_deletion_is_taken_whole_from_the_alive_side`

## 再判定の条件

- 時計のずれで古い方が勝った報告が来たら、HLC（ハイブリッド論理時計）を検討する
- 同じ記録を両方で直して消えたという報告が来たら、項目ごとに比べるか、相手ごとの前回の状態を持って
  聞く形を検討する
- 削除の記録が容量や同期の時間に効いてきたら、保持期間を検討する（今は消さない — 全端末に届いたかを
  どこも知らないため）
- 別々の記録が写しとしてまとめられた、または写しがまとまらなかった報告が来たら、印の一致の条件
  （ミリ秒・半分以上 — 決定 7）を見直すか、`CopiesDiffer` に「両方残す」の答えを足す
